# 深度研究（Deep Research）指南与可视化契约

适用于需要比较、解释或支持真实决策的问题（技术架构选型、消费品选购、方案评估、商业与产品机制深挖）。
核心目标是：**用「全网一手事实 × 知乎过来人实测 × 用户具体约束」做三角对账，给出有明确条件边界的判断，并说明什么情况下结论会反转。**

## 核心打法

**账面参数 × 知乎实测对账**：一手资料查规格与规则，知乎好回答查真实体感、隐性成本与翻车边界，穿插定制图解与交互对比

通用检索方法见 [知乎好回答深挖四步法](zhihu-research-common.md#知乎好回答深挖四步法研究与复杂搜索任务通用)。

## 默认双产物（输出到任务目录 `$RUN_DIR`）

全面深度的 `report.md` + 穿插图解交互的 `index.html`<br>（调用 `scripts/zhihu-research-render.py`）

## 一、怎么把问题拆准、搜深

1. **先锚定决策分水岭，不漫无目的扩题**
   - 拿到问题后先问：**用户在什么真实约束下做哪个决定？**（例如选洗烘机，分水岭在「空间能否放两台、每天洗几筒、床品占比、能否接受转筒与清理绒毛」）。
   - 若用户指定了本地文档或知识库，先用 `zhihu-cli knowledge search`（或上传后再检索）提取既有方案、预算与硬约束。
2. **三路组合检索**
   - **① 找知乎母问题**：`zhihu-cli question recommend --query "核心主题" --count 10`，定位讨论最集中的母问题。
   - **② 挖知乎高赞实测与踩坑**：用 `zhihu-cli search zhihu --query "..." --count 10` 分三路搜（母问题对比、踩坑后悔、原理成本实测），并对核心母问题调 `zhihu-cli question answers --question-url "..." --limit 20`，优先挑**高赞、带具体数字或踩坑细节**的回答。
   - **③ 核全网一手账面事实**：`zhihu-cli search global --query "..." --count 10 [--filter 'host=="..."']`，查官网规格、说明书、国家标准、官方架构文档或论文。
   - **④ 关键来源补读**：对支撑核心论点的 3–5 篇关键来源，使用宿主提供的网页读取工具补读；无法访问时保留摘要，并明确未读取全文。

## 二、怎么做「账面 × 实测」对账与撰写 `report.md`

深度研究最惊艳的地方，在于**揭穿「纸面参数」与「真实落地」之间的温差**：
- **账面怎么写 vs 实际怎么翻车**：把厂商大字宣传/理论架构，与说明书小字限制和知乎过来人实测账单放在同一张表格和同一个章节里正面碰撞。
- **正反观点按「成立条件」对账**：拆出正反两派各自处在什么条件（预算、户型、团队规模、并发量），直接告诉读者「满足条件 X 选 A；处在处境 Y 选 B」。
- **让知乎好回答带着身份、赞同数与原话出场**：明确写出答主背景（如「实测 8 台洗衣机的答主 @大郭街拍」「拆机答主 @为云g（2,868 赞）」）并引用 1–2 句最一针见血的原话。

### `report.md` 结构建议（3,500–6,000 字）
1. **开门见山的决策结论**：前两段直接给出分条件建议与最容易被忽略的隐藏变量。
2. **账面参数 vs 知乎实测总表**：一张高信息密度的 Markdown 对照表。
3. **核心机制与关键争点深挖（2–4 章）**：按决定成败的关键问题推进，把一手事实与知乎代表性案例揉在一起讲透。
4. **反转信号与低成本验证动作**：列出 3–4 个具体的边界条件或下手前的验证方法。
5. **参考来源清单**：按「全网一手资料」「知乎高价值讨论」分类列出完整可点击链接。

## 三、可视化设计方法与 `visuals.json` 契约

在连续论证中挑选 1–3 个读者光看文字算不清账或看不清机制的位置，插入定制 HTML/SVG 解释图或交互组件，并在首屏配置 `summary_card`。

### 1. 最出彩的五类「对账式」可视化
| 解释任务 | 推荐形式 | 典型场景举例 |
|---|---|---|
| **纸面宣传 vs 真实实测差多少？** | 同尺度条形对比 / 标称与实测双轨图 | 干衣机标称 15kg vs 不同程序实测上限；睡眠档 CADR 衰减对比 |
| **换一个处境，该选 A 还是选 B？** | 交互式条件决策树 / 处境切换器 | 按团队人数、发版频率切换「模块化单体 vs 微服务」建议 |
| **为什么会在那个环节翻车？** | 机制剖面图 / 故障链路图 | 30m³静态实验舱 vs 新房动态挥发；分布式事务失败补偿链路 |
| **隐性成本到底藏在哪？** | 总拥有成本（TCO）与到手净利拆解器 | 一笔 $9.99 跨境订阅层层剥皮后到手净利；5 年滤芯耗材 TCO |
| **各方观点到底在争哪个变量？** | 争点象限图 / 赛道存活率矩阵 | 独立开发五大赛道存活率与立项自检矩阵 |

### 2. `visuals.json` 结构规范
```json
{
  "deck": "用一两句话点透本文的核心判断与决策分水岭。",
  "summary_card": {
    "verdict": "一句话核心建议：什么条件下选 A，什么条件下选 B",
    "points": [
      {"label": "分水岭 1 · 真实容量", "value": "标称 15kg 仅限棉麻，混合程序实测上限 4–5kg"},
      {"label": "分水岭 2 · 维护成本", "value": "无独立滤网机型半年后风道易积毛絮，烘干变慢"},
      {"label": "分水岭 3 · 连续洗衣", "value": "周末连洗两筒床品时，分体机可洗烘并行省一半时间"}
    ],
    "highlights": [
      {"author": "大郭街拍", "role": "实测8台洗衣机答主", "quote": "独立热泵烘出来的毛巾像刚出炉的面包，冷凝一体机烘完像暴晒一整天那么僵。"}
    ],
    "stats": "三角对账：核对 6 份厂商说明书 × 14 篇知乎高赞长测回答"
  },
  "blocks": [
    {
      "id": "capacity-compare",
      "kind": "comparison",
      "anchor": "原 Markdown 正文某段落或二级标题中的唯一子串",
      "placement": "after",
      "title": "纸面标称容量 vs 各程序实际可烘上限",
      "caption": "切换日常衣物与床品场景，对比标称容量与程序实测上限。",
      "html_file": "capacity.html",
      "script_file": "capacity.js",
      "width": "wide",
      "sources": [
        {"label": "博世说明书", "url": "https://..."},
        {"label": "知乎答主实测", "url": "https://www.zhihu.com/..."}
      ]
    }
  ]
}
```
- `id`：英文标识，生成的容器 ID 为 `visual-<id>`；局部 CSS 请限定在 `#visual-<id>` 作用域下。
- `kind`：`process`、`comparison`、`scenario`、`mechanism`、`timeline`、`spatial`、`chart`、`evidence` 或 `custom`。
- `anchor`：原 Markdown 顶层段落或标题中的文字子串，渲染器据此把组件插在该段之前（`before`）或之后（`after`，默认）。
- `html_file` / `script_file`：相对于 `visuals.json` 所在目录的本地文件。初始 HTML 须包含默认可读状态，JS 增强交互切换。

### 3. 渲染命令（内置标准库回退，零配置即跑）
```bash
python3 "$SKILL_ROOT/scripts/zhihu-research-render.py" \
  "$RUN_DIR/report.md" "$RUN_DIR/index.html" \
  --as-of "YYYY-MM-DD" --visuals "$RUN_DIR/visuals.json" --markdown-link "report.md"
```
